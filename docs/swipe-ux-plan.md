# 이전 스와이프형 포트폴리오 구성안 — 폐기

> 사용자 피드백으로 이 디자인은 폐기했다. 현재 기준은 [세로 스토리 디자인](vertical-redesign.md)과 실제 구현 코드다. 아래는 과거 검토 기록으로만 보존한다.

최신 사용자 방향: 스와이프 가능한 UI. 메인에는 작동하는 하드웨어의 일부 프리뷰, 별도의 Lab에는 깊은 이야기. 사진은 사용자가 전부 제공한다. 취업·인턴 목적과 AI·데이터·ML / 백엔드·서버 지원 방향을 유지한다.

## 1. 방문자가 가져갈 인상

**“시스템에 대한 호기심이 깊고, 직접 구현하고 검증하며, 팀의 결과물을 서비스까지 가져가는 사람.”**

이 인상을 만드는 근거는 다음과 같이 배치한다. 아래 역량은 포트폴리오에서 설명할 목표이며, 아직 개인 기여·측정이 확인되지 않은 내용을 이미 증명했다고 쓰지 않는다.

| 보여줄 역량 | 현재 근거 | 더 확보할 설명 |
| --- | --- | --- |
| 끝까지 구현하는 실행력 | 여행갈매기 개발·수상·지원 배포, 개인 담당 역할 | 직접 만든 기능과 출시까지 해결한 문제 |
| 기술을 이해하고 선택하는 판단 | AI·데이터·서버 작업, 연구·출판, 직접 구성한 장비 | 선택지 비교, 사용 조건, 검증 방법과 한계 |
| 깊게 파고드는 호기심 | TR 4년, EPYC 4개월, NAS·노트북 개조 | 장비를 고른 이유, 실제 시행착오, 관찰 기록 |
| 협업과 책임 | 여행갈매기 팀장, 공동연구·공저 | 역할 분담, 일정·범위 조정, 피드백 대응 |

기술 이름이나 장비 수를 늘리기보다 각 주장 옆에 실제 결과·역할·사례를 붙인다. 스스로를 낮추는 표현이나 근거 없는 숙련도 퍼센트는 쓰지 않는다. 장난스러운 캐릭터는 유지하되 상세 글은 독자가 사고 과정을 따라갈 수 있게 쓴다.

## 2. 권장 구조: 다섯 챕터 + 세로로 읽는 상세

메인은 가로로 넘기는 다섯 개의 요약 챕터로 구성한다. 프로젝트와 Lab의 긴 본문은 독립된 주소에서 세로로 읽는다. 소개 화면에서 어느 챕터로든 바로 이동할 수 있다.

| 순서 | 챕터 | 화면 구성 | 방문자가 판단할 것 |
| --- | --- | --- | --- |
| 01 | 소개 | 이름·직무·짧은 소개, 수상·논문·책 근거, 하드웨어 프리뷰 2~3개 | 어떤 일을 하는 사람이며 무엇이 기억에 남는가 |
| 02 | 프로젝트 | 여행갈매기 중심의 대표작 3개. 역할·핵심 결과·상태·상세 링크 | 맡길 수 있는 일과 실제 구현 범위 |
| 03 | 연구·출판 | KCI 논문과 출간 책, 주제와 개인 기여, 출처 링크 | 기술적 질문을 분석하고 정리하는 능력 |
| 04 | Lab | 실제 장비 사진 중심, 다섯 개의 이야기와 상세 기록 | 얼마나 구체적으로 시도하고 오래 다뤘는가 |
| 05 | About·연락 | 학력·협업 방식·활동·관심사·GitHub·개인 이메일·이력서 | 함께 일할 사람과 연락 방법 |

프로젝트에서 개별 사례를 볼 때는 상세 페이지로 들어간다. 메인 가로 스와이프 안에 또 가로 프로젝트 캐러셀을 넣지 않는다. 세 프로젝트 요약은 세로 목록으로, 상세 사진은 클릭 확대 또는 세로 배치로 제공한다.

채용 맥락에서는 여행갈매기 결과가 첫 화면에도 짧게 보이게 하고, Lab은 메뉴와 프리뷰에서 즉시 접근할 수 있게 한다. 하드웨어 서사의 비중은 유지하면서 깊이 읽을지는 방문자가 선택한다.

## 3. 첫 화면 문구와 비중

추천 문구:

> **하드웨어부터 AI 서비스까지. 직접 만들고 굴립니다.**
>
> 집에 서버를 들이고, 궁금한 것은 직접 확인합니다. 여행갈매기에서는 팀장을 맡아 AI·백엔드·서버를 개발했습니다.

이름·직무는 가까이 배치한다. 수상·연구·출판 요약은 각각 해당 챕터로 연결한다. `대표 프로젝트 보기`를 주 행동으로 둔다.

데스크톱은 소개·근거 약 60%, 장비 프리뷰 약 40%를 시작점으로 잡는다. 모바일은 소개·성과·프로젝트 버튼 다음에 장비 프리뷰가 온다. 비율은 디자인 출발점이며 실제 사진에 맞춰 조정한다.

프리뷰는 `TR 2990WX · 4년 사용`, `EPYC · 4개월 사용`, `케이스·냉각을 개조한 노트북`을 우선 후보로 둔다. 전부 나열하는 대신 선택한 장비 몇 개가 구체적으로 보이게 한다. 프리뷰 아래 문구는 **“하드웨어·서버 변태의 기록 → Lab”**으로 캐릭터를 유지한다.

비교할 대안은 첫 제목을 **“하드웨어·서버 변태, 김우현입니다.”**로 더 강하게 쓰는 방식이다. 기본안은 무엇을 만드는 사람인지까지 첫 제목에 담는 것으로 추천한다.

## 4. 대표 프로젝트는 기능보다 판단을 보여준다

여행갈매기 요약에는 다음 네 가지가 함께 보여야 한다.

- 팀장, 백엔드·AI·서버 담당.
- 개발 기간 1주일.
- DIVE 2026 발제사 2등상.
- 부산교통공사 지원을 받아 배포 중, Google Play 출시 절차 진행 중.

상세에서는 **문제 → 제약 → 선택한 방법 → 개인 구현 → 검증 결과 → 현재 한계**를 순서대로 읽게 한다. 시스템 구성도에는 본인 담당 영역을 표시한다. 실제로 한 판단 두 개와 어려웠던 문제 한 개가 긴 기능 목록보다 중심이 된다.

AI 사례는 BIUM·joongo_notify 등에서 개인 기여를 확인해 선정하고, 백엔드 사례는 Filaby·RPSMS 등을 비교한다. 개인 기여 미확인 항목에 성과 수치를 채우지 않는다. 터보퀀트 등 작업이 거의 없었던 항목은 계속 제외한다.

## 5. Lab에서 캐릭터를 충분히 보여준다

Lab 제목 제안: **“대체 어디까지 손을 댔냐면.”**

이곳에서는 ‘하드웨어·서버 변태’의 말투와 시행착오를 충분히 살린다. TR을 대표 이야기로 크게 배치하고 EPYC·BC-250·NAS·개조 노트북을 이어 보여준다.

각 상세 글의 구조:

1. **첫 사진:** 실제 작동 중인 장비 또는 가장 잘 보이는 개조 부위.
2. **왜 시작했나:** 당시 불편이나 궁금증을 본인의 말로 한 단락.
3. **무엇을 만졌나:** 부품·OS·배선·케이스·냉각 등 직접 바꾼 것.
4. **어디서 터졌나:** 예상과 다른 동작, 실패와 원인 확인.
5. **무엇을 알았나:** 실제 관찰, 측정한 결과, 여전히 모르는 것.
6. **지금은 어떤 상태인가:** 계속 사용·변경·중단 여부와 다음 선택.

TR 4년·EPYC 4개월은 개별 사용 기간이며 uptime으로 쓰지 않는다. BC-250은 두 대 구매가 확인된 사실이다. 구동·개조 결과는 추가 설명을 받은 범위로 기록한다. 노트북과 일체형 PC 개조는 다른 경험으로 둔다. 실패·미완성이라도 실제 시도와 관찰이 있으면 소개한다.

## 6. 사진과 움직임

사진은 사용자가 제공하는 실제 자료만 쓴다. 현재 구성안은 사진의 자리를 표시한다.

| 쓰임 | 우선 필요한 자료 | 표현 방식 |
| --- | --- | --- |
| 메인 프리뷰 | TR 작동 모습, EPYC 또는 개조 노트북 | 짧은 캡션과 Lab 진입 링크 |
| Lab 대표 사진 | TR 전체 모습·내부, EPYC 구성 | 크게 보고 부품·구조를 이해할 수 있게 |
| 개조 과정 | 노트북 개조 전후·근접 사진, NAS 구성 | 전후를 나란히 또는 세로로 비교 |
| 실제 사용 맥락 | 책상·배선·작업 화면·당시 기록 | 무엇을 하고 있었는지 설명하는 캡션 |
| 성과 근거 | 서비스 화면·수상 자료·책 표지 | 관련 프로젝트와 출판 카드에 배치 |

‘돌아가는 모습’은 켜진 장비의 사진으로도 표현할 수 있다. 짧은 실제 영상이 제공되면 선택적으로 사용한다. 메인 사진 2~3개, Lab 이야기마다 전체 1장·세부 2~4장을 시작점으로 하되 자료를 보며 고른다.

영상이 있을 때는 무음·정지 제어와 정지 이미지 대체를 제공하고, 첫 화면에서 여러 영상을 동시에 재생하지 않는다. 움직임 줄이기 환경에서는 정지 이미지를 사용한다. 제공받지 않은 장비의 작동 영상이나 실시간 계기판을 만들어 넣지 않는다.

## 7. 스와이프가 탐색을 방해하지 않게

- **직접 이동:** 이름 있는 상단 메뉴와 현재 챕터 표시, 이전·다음 버튼 제공.
- **입력 방식:** 터치 좌우 스와이프, 수평 트랙패드, 버튼과 키보드 탐색. 세로 휠을 강제로 가로 이동으로 바꾸지 않는다.
- **본문:** 내용이 길면 정상적인 세로 스크롤을 허용하고, 화면 높이에 맞춰 글을 자르지 않는다.
- **전체 보기:** 다섯 챕터를 세로로 펼쳐 빠르게 훑을 수 있게 한다. 이력서·연락처는 별도 경로로 바로 접근한다.
- **자동 이동:** 챕터를 자동으로 넘기지 않는다. 사용자가 읽는 속도를 유지한다.
- **상세·뒤로가기:** 실제 구현에서는 `/projects/galmegi`, `/lab/tr-2990wx` 같은 직접 주소를 제공하고, 뒤로가면 기존 챕터와 위치를 복원한다.
- **접근성:** 현재 항목 알림, 명확한 포커스, 충분한 버튼 영역, 동작 줄이기 지원.
- **초기 로딩:** 핵심 소개·역할·성과는 사진이나 애니메이션이 준비되기 전에도 읽을 수 있게 한다.

기술 구현 후보는 기본 문서 구조 위에 스와이프를 더하는 방식이다. 디자인 확정 전 특정 슬라이더 라이브러리를 결정할 필요는 없다.

탐색·키보드·알림·움직임 제어 기준은 [W3C WAI 캐러셀 가이드](https://www.w3.org/WAI/tutorials/carousels/)를 참고했다. 다섯 챕터의 순서와 콘텐츠 비중은 이 사용자와 채용 목적에 맞춘 구성 제안이다.

## 8. 이번에 검토할 결정

- 첫 제목은 역량 중심으로 두고, ‘하드웨어·서버 변태’는 프리뷰·Lab에 명확하게 남기는 기본안.
- 메인은 다섯 챕터로 요약하고, 개인 기여·설계·하드웨어 과정은 상세로 분리.
- 하드웨어 사진은 첫 화면에서 호기심을 만들고, Lab에서 구체적인 경험을 보여주게 사용.
- 구성안의 선택지를 눌러 첫인상 문구와 프리뷰 비중을 비교한 뒤 실제 사진에 맞춰 디자인 조정.

현재는 구성 탐색 단계다. 사이트 구현·배포, 최종 사진 배치와 공개 원고 확정은 이후 단계다.
